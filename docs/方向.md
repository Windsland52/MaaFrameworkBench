# 这个项目要做什么

> 这份讲「要做什么、做到哪一步、下一步是什么」。
> **状态不写在这里** —— 写下来的状态会过期，跑 `pnpm status` 当场读仓库。

## 一句话

把「用 AI 开发 MaaFramework 应用」这件事变成**可测量**的：

给被测系统一道题和一个"设备"，它交出 pipeline / interface / custom 代码，
我们**把它跑起来**，判「业务达成没有」，最后回答**哪套组合更会做这件事**。

判分的本质是**执行** —— 不是文本比对，也不是判官打分。

## 做完了长什么样

**输入**：一批任务包（几十个）+ 一批被测系统（harness × model × skill 的不同组合）
**输出**：一份报告，回答四个问题

| 问题                                     | 靠什么回答                                     |
| ---------------------------------------- | ---------------------------------------------- |
| 每套系统在**哪一类**任务上过、哪一类不过 | 最小项 → 能力 → 维度（契约 §4）                |
| 同一套系统反复跑**稳不稳**               | 分布 + `pass^k`（k 次全过才算过）              |
| 花了多少                                 | token / 时间（`run.json` 的 `usage`）          |
| 哪条**改动**带来了增量                   | 对照臂：裸模型 / +文档 / +示例 / +skill / 全量 |

报告里**每个分数都要标是在哪种环境上得的** —— 三种环境保真度不同，混着比没有意义。

## 机器长什么样（五块积木）

| 积木       | 干什么                                     | 现在在哪          |
| ---------- | ------------------------------------------ | ----------------- |
| **任务包** | 一道题：题面 + 环境声明 + 断言（held-out） | `tasks/<id>/`     |
| **环境**   | 被测 pipeline 的"设备"：喂画面、响应输入   | `src/env/<type>/` |
| **执行器** | 摆工作区 → 真跑 → 收证据 → 落 run 目录     | `src/runner/`     |
| **判分器** | 只看 run 产物，判业务达成没有              | `src/scorer/`     |
| **报告**   | 把一批 run 汇总成上面那份报告              | 还没建            |

**一次 run 发生什么**（这是理解整套东西最短的路径）：

1. 执行器按白名单把任务包摊成一个临时工作区 —— 断言、held-out 画面绝不进去
2. 被测系统把产出写进这个工作区（`resource/base/pipeline/`）；**写下去那一刻就是"提交"**
3. 起**子进程**，MaaFW 真的跑它；超时硬杀整个进程组
4. 过程留三份证据：节点/识别结果的事件流、环境侧记的每次输入、框架自己的日志。
   跑完把工作区拍成快照并算哈希 —— 之后**只认这个哈希**，提交后再改的一律不看
5. 判分器只读快照和证据，拿题面里的断言判；**框架报 succeeded 不算通过**
6. 报告层把很多 run 汇总成结论

## 素材从哪来

按「这份东西的复杂度能不能自己造」分三条线：

| 素材                                          | 怎么来                    | 为什么                                                                         |
| --------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------ |
| **单件素材**（一屏画面、一份日志）            | **自己造**                | 版权、污染、分发三件事一次解决；难处照真实案例学                               |
| **项目载体**（修 bug / 日志分析要的真实项目） | **借真实项目，钉 commit** | 复杂度造不出来（公开的 Maa 项目动辄 300–500 个 pipeline 文件）；缺陷由我们注入 |
| **锚点**（预测效度）                          | 少量真实案例              | 回答「自制条件能不能预测真实条件」，不进主数据集                               |

一条共同原则：**看真实案例学「难在哪」，不搬它的数据。** 代价是「整体真实感」未必到位，
所以一批题造完必须跑**地板 / 天花板**：如果所有系统都满分，这批题就是没造好。

### 造题靠注入，不靠挑案例

载体是真的，缺陷是我们注入的 —— 记住注入点，ground truth 就有了：

```
① 注入前跑一遍，确认目标行为是好的   → 记成「基线」
② 注入后跑一遍，确认它确实坏了       → 记成「注入点」
```

两份都是机器产出的。**回归比的是基线快照，不是「全绿」** —— 真实项目本来就有失败。

题面只给**现象**（跑不通 + 日志）和**要求**（期望行为），**不给原因、不给方案**。
也没有「唯一正确的修复 diff」这种东西：同一个 bug 修在哪一层都可能是对的，
比对 diff 会把多种正确解判错。

### 一份夹具，多个读数

| 读数            | 从哪读                     | 对应最小项     |
| --------------- | -------------------------- | -------------- |
| **行为达成**    | 跑一遍，判业务状态         | 3.3.1 改对     |
| **定位 recall** | 注入点在不在它改动的集合里 | 3.2.1 定位准确 |
| **修改精度**    | 改动规模 vs 注入规模       | 3.3.2 改得克制 |
| **回归**        | 其它目标还过不过           | 3.3.3 改得通用 |

**分读数，不分案例** —— 分开造夹具会把案例数砍半，而契约 §4 要求每个最小项至少 5 例。

**难任务上定位 recall 是唯一还能区分系统的读数**：两个系统都没修好，一个改在注入点上、
一个改了一堆无关文件，修复通过率都是 0，差别只剩这个数。这正是契约 §4 要的「分段阶梯」。

## 被测系统怎么跑

用 **DSH 的 headless 模式**，不自建 harness：

```sh
dsh --profile headless --json --patch <overlay.yml> "<题面>"    # cwd = 工作区
```

- 事件流里带 provider 的账（`status/step_end` 的 `usage`）—— 这就是 `run.json` 的 `usage` 来源
- `--patch` 按 run 叠一层配置：模型、沙箱模式、工作区根都是配置项 → **一次 run 的身份钉得死**
- 会话完整落盘，可当证据留档

**它的沙箱只关写、不关读**（官方口径 `reads stay unconfined`）。读隔离要靠真边界
（容器 / 关掉自动挂载的 WSL 发行版 / 独立用户 + ACL），不是配置能解决的。

**自测手段给** —— 被测系统能跑 MaaFW 验证自己的产出，这一点影响任务难度。
代价约 91 MB（maa-node 61 + OCR 模型 30），依赖目录必须放**仓库外**：
用软链指回仓库等于给了一条通往参考答案的路。

## 从今天到那一天

按**依赖**排，不是按工作量排：

1. **接第一个真被测系统** —— 现在提交产出的是手写的参照实现，它只证明管道通、判据会挂。
   真系统一进来，很多现在看不见的问题会立刻暴露（题面清不清楚、任务难不难、判据够不够严）。
   同时要把防作弊补齐（还缺什么见 `TODO.md`），否则第一批数字不可信。
2. **造题** —— 注入已知缺陷合成任务，不靠人工挑案例；把覆盖面从很低的地方顶上去。
   这一步决定"能不能报数"，因为**每个最小项少于 5 个案例就不该报通过率**（契约 §4）。
3. **第二个环境** —— `frames` 一屏只有一条路径，多路径没有环境承载。
   而且"在自制环境上测出的排名，能不能预测真实录制上的排名"是**唯一能证明自制环境没白造**的实验。

## 已经定死的（不用再讨论）

TypeScript 不是 Python · 环境分三档 · 判分只判业务达成、只判首次提交 ·
不做：用 CMP 建项目 / 通用排行榜 / 操作能力 / 依赖真实设备的行为 / "从零做完整应用"当独立轴。

## 还没定的（要人拍板）

- **这东西是自用工具还是对外发布物？** 决定文档、许可、数据集分发要不要按公开标准做。
- **第一次真正要回答的问题是哪个**："我们的 skill 有没有用"（工具链评估），
  还是"哪个模型更会写"（模型评估）？两个问题的对照臂设计完全不同。
- **真实素材（录制件 / 日志 / 帧）从哪来** —— 决定 `replay` 环境能支撑多少任务，
  也决定「锚点」那类预测效度实验做不做得起来。
- **用真实项目当载体的许可** —— 公开的 Maa 项目基本是 AGPL。不分发（按 commit 拉取）大概率没问题，
  但这是要确认的事，不是顺手能定的。
